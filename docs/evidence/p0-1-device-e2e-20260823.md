## 结论

**Confirmed by packet capture or runtime observation**：本地 SDK、区服列表、游戏 TCP 登录、启动数据和主界面链路已在设备上完成两次。第一次和第二次均通过：

```text
server/list -> SDK token validate -> CSLoginReq(3)
-> SCHandShakeNtf(7) -> SCLoginAck(4)
-> SCStartupInfoNtf(25) x 4 -> SCStartupInfoEquipNtf(26)
-> SCStartupInfoHeroNtf(27) -> SCStartupInfoEndNtf(28)
-> 主界面初始化请求 -> 主界面
```

第二次是在强制停止应用后重新启动，并再次点击“开始游戏”。设备最终停留在游戏主界面，不是只保持 TCP 连接。

## 首次启动

**Confirmed by packet capture or runtime observation**：服务端 trace 记录客户端登录字段 `open_id=1`、`account=test`、`auth_type=18game`，登录被接受，角色匹配到 `role_id=1`。本地第一轮关键帧为：

| 方向 | 消息号 | body 长度 |
| --- | ---: | ---: |
| C -> S | 3 | 893 |
| S -> C | 7 | 18 |
| S -> C | 4 | 9 |
| S -> C | 25 | 557 |
| S -> C | 25 | 38 |
| S -> C | 25 | 59 |
| S -> C | 25 | 994 |
| S -> C | 26 | 2 |
| S -> C | 27 | 114 |
| S -> C | 28 | 0 |

原始启动抓包对应长度为 `3=899`、`7=18`、`4=9`、`25=152/38/59/994`、`24176=4`、`26=2`、`27=114`、`376=116`、`28=0`。本地已确认的差异是：

- 登录 body 为本地账号和本地轨迹，长度为 `893`，不应与原始账号的 `899` 字节相同。
- 第一段 `25` 被本地持久化角色状态和动态字段改写为 `557` 字节；其余三段和 `26/27/28` 长度一致。
- 本地没有发送原始抓包中的辅助通知 `24176` 和 `376`，但客户端仍完成 `28` 后的主界面初始化并进入主界面。

## 主界面和重连

**Confirmed by packet capture or runtime observation**：收到 `28` 后，设备继续发起并收到以下响应：

```text
23/24, 24146/24147, 349/350, 170/171, 166/167,
368/369, 327/328, 61/62, 24152/24153, 24183/24184,
59/60, 1/2 heartbeat
```

`main-interface.png` 显示主界面已加载，等级为 `Lv.4`，顶部显示金币 `2100`、钻石 `50` 和体力 `20/20`。`device-logcat.txt` 同时记录 `LoadTutorial`、`EnterGame_LoginTask` 和主界面福利初始化。

随后执行：

1. 强制停止 `com.IdolTime.Cards.game18`，断开已有游戏 TCP。
2. 重新启动应用，SDK `validateToken` 返回成功，重新显示区服“天空岛”。
3. 再次点击“开始游戏”，服务端第二次接受 `CSLoginReq(3)`。
4. 第二轮再次收到完整 `7/4/25x4/26/27/28`，并进入主界面。

第二轮的启动帧长度和第一轮一致；两个 TCP peer 和完整帧顺序记录在 `trace-summary.json`、`game-trace-first-start.txt`、`game_tcp.log` 和 `device-logcat-reconnect.txt` 中。
